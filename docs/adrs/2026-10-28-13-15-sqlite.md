# ADR: Use SQLite with Exposed as the database

- **Status**: Accepted
- **Date**: 2026-10-28

## Context

The app needs to store vocabulary, and later the user's learning progress (e.g. SRS review schedules). The vocabulary itself is maintained in YAML files in the repository (`vocabulary/<language>.yaml`), which are the source of truth.

The requirements are modest: one user, a small amount of data, cheap self-hosting, and simple local development. See the [initial vision](../initial-vision.md).

## Decision

- We use **SQLite** as the database, stored in a single file (`data/language-trainer.db` by default, configurable with the `DATABASE_FILE` environment variable).
- We access it from the Ktor server with **Exposed** (JetBrains' Kotlin SQL library, DSL API) and the `sqlite-jdbc` driver.
- On startup, the server loads every vocabulary YAML file, validates it (including duplicate detection on word + category), and syncs the result into the `words` table: new words are inserted, changed words are updated and words removed from the YAML are deleted.
- **No migration system yet.** Tables are created with `SchemaUtils.create`, which only adds missing tables and never alters existing ones. Small changes, like adding a column, are done by hand in `connectDatabase`.

## Why SQLite and Exposed

- **Zero operations**: SQLite is an embedded, serverless database. There is no database server to install, run or pay for, which fits the single-user, low-cost goal.
- **One file**: the whole database is one file that is easy to inspect, back up, copy or delete.
- **Good enough performance**: a single user with thousands of words is far below SQLite's limits.
- **Real SQL**: unlike plain files, we get transactions, indexes and unique constraints (e.g. one word per language + word + category), which will matter once progress data is stored.
- **Kotlin-first access**: Exposed is maintained by JetBrains, uses type-safe Kotlin instead of SQL strings, and is a good way to learn idiomatic Kotlin.

## Why no migrations yet

As long as the database only holds vocabulary, it can be fully rebuilt from the YAML files at any time, so there is nothing to migrate. A migration tool (such as Flyway or Exposed's migration support) should be added **before** storing data that only exists in the database, such as learning progress.

## Alternatives considered

- **PostgreSQL**: powerful, but requires running and hosting a separate server, which is too much overhead for a single-user app.
- **H2**: also embedded, but SQLite is more widely used, has better tooling, and its files can be opened by many other tools.
- **No database (read YAML into memory)**: simplest for vocabulary, but offers no good place to store learning progress later.

## Consequences

- **Positive**: no infrastructure, quick setup, easy to reset, and a clear path to storing progress data.
- **Negative**: SQLite allows only one writer at a time and runs on a single machine, which is fine for one user but limits future scaling. Until a migration tool is added, schema changes to existing tables need hand-written SQL (see the update below). `alternatives` and `tags` are stored as JSON text to keep the schema simple, so they can't be queried efficiently with SQL.

## Update: training results are stored (2026-10-28)

The database now also holds `training_sessions` and `answers` (every answer given, with its result). The correct/almost/incorrect counts per word are calculated from `answers` and not stored. This is data that does **not** come from the YAML, so:

- **Deleting the database file now loses all training results.** Only do that if you accept losing them.
- We deliberately still use `SchemaUtils.create` for the new tables instead of adding a migration tool now. New tables are created automatically on existing databases. The next change to an *existing* table should come with a migration tool (such as Flyway or Exposed's migration support) instead of more hand-written `ALTER TABLE` statements.
- Answers reference words by ID without a foreign key, so they are kept when a word is removed from the YAML. They no longer show up, and because word IDs are never reused, they won't be attached to another word. Renaming a word in the YAML creates a new word, so its history starts at zero.
