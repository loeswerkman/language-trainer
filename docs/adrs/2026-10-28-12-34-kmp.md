# ADR: Use Kotlin Multiplatform (KMP)

- **Status**: Accepted
- **Date**: 2026-10-28

## Context

Language Trainer is a personal, single-user vocabulary app (see [initial vision](../initial-vision.md)). It starts as a web app with a Ktor backend and should be able to be made available easily across platforms.

The technology choice is driven by three wishes:

1. **Learning Kotlin**: the project is a training ground for learning Kotlin across the full stack.
2. **A readable and testable codebase**: the code should be clean, well-structured and easy to test.
3. **Scaling across platforms**: the app should be able to easily migrate to iOS, Android, macOS and/or Windows in the future.

## Decision

We use **Kotlin Multiplatform (KMP)** as the foundation of the project, with **Compose Multiplatform** for the UI and **Ktor** for the server.

## Why KMP is the right approach

- **One language everywhere**: backend, shared logic and UI are all written in Kotlin. Every part of the project helps with learning the language, and there is no context switching between languages.
- **Shared, platform-independent logic**: business logic (SRS scheduling, answer evaluation, data models) lives in `commonMain` as pure Kotlin. It is written once, works the same on every platform, and can be tested once with `commonTest`.
- **Readability and testability**: Kotlin is concise and null-safe, which keeps the code readable. Keeping the core logic free of platform code makes it easy to unit test without UIs, devices or emulators.
- **Native reach to all target platforms**: KMP compiles to the JVM (Android, macOS and Windows desktop, server), to native code (iOS) and to JS/Wasm (web). Compose Multiplatform lets the same UI code run on Android, iOS, desktop and web.
- **Incremental growth**: we can start with web and add new platforms as extra targets in the existing project. Shared code stays as it is, and platform-specific behaviour can be added through `expect`/`actual` only where needed.
- **Native performance and APIs**: unlike web-wrapper approaches, KMP produces native apps and still gives direct access to platform APIs when needed.

## Alternatives considered

- **Separate native apps (Swift, Kotlin/Android, etc.)**: the best platform fit, but means duplicating logic in several languages, which is too much effort for a single-developer project.
- **React Native (TypeScript)**: good cross-platform support, but it doesn't use Kotlin, so it doesn't help with the learning goal.
- **Python**: the language I'm most experienced in, which would make early development easy. It was discarded because it isn't well suited to building native cross-platform apps. iOS and Android have no official support for Python apps, and the frameworks that try to fill this gap (such as Kivy and BeeWare) are niche and less mature. On desktop, Python apps also need a bundled interpreter to be distributed. It also makes it harder to write reliable code compared to statically types languages such as Kotlin.

## Consequences

- **Positive**: one language and one codebase, shared and well-tested core logic, and a clear path from web to iOS, Android, macOS and Windows.
- **Negative**: KMP and Compose Multiplatform are younger than native toolkits. Some libraries are not multiplatform yet, and the iOS and web targets are less mature. Building for iOS also requires a Mac with Xcode.
